# Three and four player races

Rush 2 is built for two local players. src/players4.cpp adds players 3 and 4; this page covers the game code it
leans on. The relocated per-player and per-view arrays are listed in src/players4.cpp (`moves`) and generated by
tools/players4/relocate.py.

## Controllers and joining

There is no fixed controller-to-player mapping. src/input.cpp gives each enabled controller the first free N64 port
when it presses a button (the Controls tab only enables or disables them; the keyboard is one more controller). The game then makes whoever presses START a player: player 1 on the title screen
(func_800A6B58, hooked so player 1 is the first port with a device), player 2 with func_80093E08, players 3 and 4 by
src/players4.cpp's `update_joining` on Select Player. Old players.json files (a pinned controller per player) are
migrated at startup: only whether the keyboard is on carries over.

Players 3 and 4 skip Select Player. They race with their port's own record (0x8010D740 + port * 0x6C0) or the
profile last chosen on the port, unless another player already uses that profile.

## Button masks

Each player record (0x800C2140 + player * 0x28) holds, at +0xC to +0x1D, one u16 per action with the N64 buttons
bound to it. func_8009FEE8 (save_copy_player_record) fills them from the port's binding table (0x80125A70 + port * 9)
for the game's player count, which is 2 in the menus, so players 3 and 4's stayed zero and their cars wouldn't drive.
They are copied from player 1's at race start; the binding tables are locked to the game's layout (src/controls.cpp),
so every port's masks are the same. func_80076A00 sets each player's pedals from them every frame (func_80076854).

## Finish overlay

func_800A0FB4(1) runs every frame of a race once a player has finished, and in race over. It keeps the overlay of
each player's place (layout table 0x800BF328, 7 entries, list in D_800E7BC0) and rebuilds it only when player 1's or
2's place shows or hides: the place widgets (callback func_800B5A90) set D_800BF318[player] each frame, and the
overlay was built with D_800BF444[0-1] equal to D_800BF318[0-1]. Players 3 and 4 use D_800BF318[2-3] (unused by the
game), and a hook before its first build forces the rebuild path whenever those change, so their copies of player 2's
entries are added and laid out with the HUD.

The rebuild also makes the dark box behind each shown place with func_80093B38 (x0, y0, x1, y1 in $a0-$a3, alpha 0xC0
at $sp + 0x10): player 1's at 0x63, 0x1D - 0xDD, 0x3F and player 2's at 0x63, 0xAB - 0xDD, 0xCD (with 2 views). Those
are for views stacked top and bottom, so in a split screen they are skipped and src/players4.cpp's `finish_boxes`
makes one per finished player at the same places, tagged as part of that player's place: src/hud.cpp moves each
place and its box together to the middle of the player's half or quadrant. func_80093B38 keeps its boxes at
0x800C4254 (0x20 each: +0 in use, +1 kept (its last argument, $sp + 0x1C: func_80093A84(0) frees only the boxes
without it), +2 fill color, +6 edge color, +0xC five HUD elements, the fill and four edges, each with the box's callback
at +0x28 and parameter at +0x2C from $sp + 0x14 and + 0x18). It had room for 10; tools/players4/relocate.py moves it to
0x802FA000 with room for 20 (us.toml raises the count in func_80093B38's three tests, 0x80093B80, 0x80093B88,
0x80093B94), as four players' stunt panel boxes (below)
and their place boxes at race over need 14.

The table's entries (x, y at +4, +6; callback +0x20, parameter +0x24): entry 0 is func_800B5CAC at 0x58, 0x48; entries
1-3 are player 1's place (func_800B5A90, parameters 2, 0, 1) at 0x60, 0x22 twice and 0x9B, 0x22 ("PLACE"); entries 4-6
are player 2's (parameters 0x102, 0x100, 0x101) at the same x and y 0xB0. The track map (HUD layout 0x800C2DB4 entry
102, func_800B8188) is at 0xD0, 0x50 and its 4 x 4 car dots (entries 103-110, func_800B8900) move over x 0xD3 to
0xD3 + 0x58, so "PLACE" reaches the map's bottom left corner. A dot there is centered on both images, and
src/hud.cpp's grouping linked "PLACE" to the map through it: in widescreen "PLACE" jumped to the right edge with the
map until the car drove on (seen on an SF Rush track whose map has a tip in that corner). The place's images now link
only with each other.

src/hud.cpp links touching fills into one element only within one of these boxes (`hud_widget_boxes`): after a
checkpoint, the box behind the blinking bonus time banner (BONUSTIME4 at 0x60, 0xA0, blinked by func_80060F24 while
its end time 0x8010C3C4, set by func_8008F220, is over a second ahead of the clock 0x80117488) spans 100, 155 - 219,
180, and its bottom row is the top row of the stunt score panel's box (193, 180 - 297, 219, shown on every track with
Stunts on All Tracks). Grouped, the panel took the center anchor in the widescreen HUD while the banner was up.
RUSH2_TEST_BONUS_TIME=<seconds> keeps the banner up from that game clock time, to test without reaching a checkpoint.

## Stunt panel

The stunt panel shows in the stunt arena and on every track with Stunts on All Tracks. The race HUD setup
(func_800A06F8, 0x800A0944-0x800A0A80) builds two boxes per player with func_80093B38 (alpha 0xC0, kept): the
BEST / TOTAL scores' at x 193-298 and the trick name's at x 22-127, at y 180-220 with one player, else player 1's at
y 70-110 and player 2's at y 180-220. Their callback `hud_stunt_box_visible_80060E34` takes (player << 4) | box (0
scores, 1 trick name) and hides a box unless the panel shows (track 11, STUNT1, or the 0x8010C200 cheat byte), the
player is in the race, and for the trick name's, while the player's flag 0x8010C070 is clear.
`hud_widget_text_cb_player_stats_800B7654` (HUD layout entry 111, one callback widget) prints every player's text in
a loop ($s6 = the player): the trick name centered on x 74, "BEST" and "TOTAL" right-aligned at x 258 and their
values from x 268, on rows 44 and 28 pixels above y 120 (one player, or player 1 of two) or y 230 (every other
player). It sets the text scale 0x800BEF48 to 0 while it prints, so the text is drawn at once, not queued.

With 3 or 4 players, src/players4.cpp's `stunt_boxes` adds players 3 and 4's boxes (copies of player 2's; hooked at
0x800A0A84, before the HUD's widgets are created, so the text callback's widget comes after them and its text is
drawn over their translucent fill, as players 1 and 2's) and
`tag_stunt_boxes` tags every stunt box's widgets with their player and role (StuntScore, StuntTrick).
In quadrants each box is drawn at half size about its top left corner, placed by the HUD layout's rules
(docs/hud_layout.md#rules): in the stunt arena the scores' box in the bottom outer corner of the quadrant and the
trick name's on it; with Stunts on All Tracks in a race, under the corner panel (else beside the outer column), the
trick name's box in the scores' place while it shows. The boxes keep room only where the stunt panel can show (the
stunt arena, the cheat byte 0x8010C200), and in the stunt arena players 2-4's time and position, which never show,
take none. The stunt arena is told by the race's track id 0x8010C3F0 = 11.
While the text callback runs (hooks at its entry and its return, 0x800B7AE8), `rush2_hud_print` moves each string with the box of the player in $s6 that it is printed over
and scales its rectangles about the same corner. Side by side, the boxes keep the game's layout moved to the half.

## 2D display list

The HUD, menus and text after the 3D views go in the 2D display list, one of two buffers alternating by frame:
`gfx_2d_list_begin_800B3A20` flips 0x80119850 and points the cursor 0x80125ABC at 0x8011CDB8 + frame * 0x4650, and
`gfx_2d_list_end_800B39AC` writes the end and returns the list's start. A buffer holds 2250 commands and the second
ends where the HUD element pool's counts begin (0x80125A58). Four players' HUDs in a race with a battle, DEATHS, the
odometer and the stunt panels outgrew it: the overflow corrupted the element free list, and the game crashed in
`hud_widget_free_8005FED8` when the pause menu was set up at the start (or the HUD stopped drawing). src/hud.cpp
moves the buffers to 0x80AE0000, 0x10000 bytes (8192 commands) each, hooked at 0x800B3AF4 and 0x800B3A18; the game
heap's top is lowered from 0x80B00000 to 0x80AE0000 for them (src/assets.cpp, us.toml).

## Race over and post-race

func_800AE670 is the game's state machine (D_8010C0D0). func_8008E8EC marks a car finished (+0xEA, race time +0xEC)
and sets D_8010C0E0 once as many human cars as players have finished. State 3 goes to 4 when players 1 and 2 have
finished (hooked to also wait for players 3 and 4). State 4 runs func_800AAE20 once (stops the player engines with
func_8008C49C, rebuilds the finish overlay with the race over box) and moves to 5, which shows every player's place
and GAME OVER for 4 seconds (or until START) and moves to 6.

State 6, func_800A952C, saves each player's record to their profile, enters lap and race times into the track's
tables and runs the name entry. Its per-player arrays exist for two players (D_800D3628: 2 tables x 2 players x 0x18,
with loops that stop at 0x800D3688; D_800D2940, D_800D39A8, D_800D3F28, D_800E79C8, D_800E7D20, D_800E7D3C,
D_800E7D54, the names at D_800D3A40), and four players overflowed them into the audio voices (a sound then read from
a bad ROM address in the audio thread). The player and view counts go back to 2 at state 6, so race over keeps all
four players and the records are players 1 and 2's.

## Pause and Controller Setup

func_800AFD44, the pause menu step, loops over every player's record; START from any of them pauses the race at
0x800AFE14 with $s6 = that player (src/players4.cpp keeps it). Every player's own pressed buttons then drive the
menu. The Controller Setup screen (func_800AD7E4, text func_800B6134) has two panels; opened from the pause menu by
player 3 or 4 they show players 3 and 4: its text loop's first record pointer ($sp + 0x54, stepped by 0x28 per
panel) and the "PLAYER %d" titles ($a3 before the sprintf at 0x800B6424) move on by two players, and
src/controls_menu.cpp edits ports 3 and 4's bindings.

## Sky in split screen

Rush 2 builds the sky only for one player: `sky_setup_800A45A8` returns at 0x800A4600 when the player count
(0x8010C3E2) is 2 or more, to save drawing time. SF Rush (`sky_setup_800A7494`) and Rush 2049 draw it in split screen,
so `rush2_track49_sky_players` (src/rush2049/track2049.cpp) builds it for any count, on every track but the Rush 2049
obstacle course (no sky model).

- **Per-view arrays.** The sky's per-view arrays had room for two views, with other globals right after them:
  0x80125B68 (sky model matrix node), 0x80125B90 (24 dome polygon pointers per view, stride 0x60), 0x80125C58,
  0x80125C68, 0x80125C78 (camera x) and 0x800D0168 (camera z). tools/players4/relocate.py moves them to four-view
  copies; `func_800A12A4` (clears them) and `render_sky_cloud_scroll_8008918C` (moves them each frame) follow.
- **Dome.** Each view gets its own 24 world polygons (flags 0x2200 | view bit), 96 of the pool's 200 with four views.
  `rush2_players4_poly_mask` lets views 2 and 3 draw views 0 and 1's world polygons, but not the dome's pieces (flag
  0x2000 at a far primitive depth), which are centered on their own view's camera.
- **Dome fade.** With the FOG option below 2, `render_sky_cloud_scroll_8008918C` takes (2000 - far) x 0.512 - fog
  start x 2 + 1992 off the dome's vertex alpha (at 0x80089274, from the view's +0x38 and +0x4C, which
  `race_fog_zone_setup_80081074` sets from the tables at 0x800CA244 (far) and 0x800CA258 (fog start), s16
  [players][5 FOG options]). One player with FOG 1 (far 2000, fog start 996) gives 0; split screen (far 1100) gives
  460, a dome faded out entirely. `rush2_players4_sky_fade` takes off the difference between the two-player and
  one-player table values for the FOG option, so the dome fades as it does for one player, fog zones included.
- **Sky model** (Las Vegas, the stunt arena, Rush 2049 tracks). Scene nodes link into two views' lists only
  (`node_link_search_8007F570` tests mask bits 1 and 2), so the nodes made for views 2 and 3 are never drawn and those
  views draw views 0 and 1's. `rush2_players4_sky_view` (hooked at `pvs_apply_8007C27C`, before each view is drawn)
  moves the node to the view's own camera x and z; the scene walker builds the node's matrix as it draws, so views 0
  and 1 are already done, and the next frame's update puts them back.

## Arrays that share an address with a table

The relocator moves every `lui`/load pair whose address falls in a moved range, so a table that happens to start inside
a moved array is moved too, and its entries past the array's end read the new copy's zeros. Those sites are in
`EXCLUDE` in tools/players4/relocate.py and keep their original address.

- **Frame Scale cheat** (issue 34). The cheat byte 0x8010C43C indexes an f32 table at 0x800BFC80 (1 = 0.6, 2 = 1.2,
  3 = 1.5; 0 means off and is never read) that `carselect_build_preview_car_8008813C` (0x800887A8/0x800887B0) and
  `car_matrix_copy_and_apply_8009ABDC` (0x8009AC00/0x8009AC14) multiply into the car matrix's Y column. 0x800BFC80 is
  inside the camera timer array 0x800BFC7C (one f32 per view), so relocated it read 0.0 for every option and drew the
  car flat.
